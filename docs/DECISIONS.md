# Decisions

Deviations from `ishaara_backend_implementation_plan.md`, one line each.

- M0: The project lives at the repo root instead of an `ishaara-backend/` subfolder.
- M0: Secrets and resource names (`GEMINI_API_KEY`, buckets, etc.) default to empty strings so `/healthz` and tests run without them.
- M0: The Dockerfile also copies `README.md` because `pyproject.toml` declares it as the package readme.
- M1: Added a `youtube_unavailable` (502) error for persistent YouTube Data API failures; the plan's error list has no code for it.
- M1: `isodate` and `firebase_admin` are in mypy's `ignore_missing_imports` override because they ship no type stubs.
- M2: The Interactions API takes video clip offsets as strings with an `s` suffix (`"590s"`), not integers; `GoogleGeminiGateway` formats them that way.
- M2: Replaced the plan's pointing-word detection with two-pass gap detection. Pointing cues repeated what the teacher had just said aloud (e.g. reading a definition) and missed silent board content. Pass 1 (video, `analyze_clip`) returns the transcript plus every visual event; pass 2 (text, `judge_gaps`) rates each event `fully_spoken`, `partly_spoken` or `not_spoken`; code keeps the last two. `PointingMoment`/`TimedPointingMoment` became `VisualEvent`/`TimedVisualEvent`, and `GeminiGateway` gained `judge_gaps`.
- M2: Tuning pass 2 is cheap because `uv run ishaara analyze <url> --from-fixtures` reuses the saved pass 1 file and calls only the text model. Fixtures are `<id>_w<start>.json` (pass 1) and `<id>_w<start>_gaps.json` (pass 2).
- M2: Findings on two 3-minute clips: the judge needs the rules "look 20 s either side", "a lone bracket or symbol is not a gap" and "labels, arrows, tick marks and shapes are gaps unless named aloud". Judgements vary slightly between runs.
- M2: `NarrationCue.narration_text` defaults to `""` (merging runs before narration exists) and `NarrationCue` gained `gap_summary` (what a listener would miss).
- M2: `write_narration`, `synthesize_speech` and `answer_question` on `GeminiGateway` are placeholder signatures and may change in M4 and M6.
- M2: Only two videos were used: the English circular-track lecture covers both "English math" and "diagrams", and the Hinglish power-set lecture is the third category. The video `resolution` option was not tried.
- M2: Timestamp normalization can misread a window whose events all fall in its first `window length` seconds as clip-relative; real windows have many events, so this was left as is.
- M3: Storage is behind `VideoRepository` / `UsageRepository` ports (`clients/repositories.py`) with in-memory, Firestore and Supabase (Postgres via `psycopg`) adapters chosen by `DATABASE_BACKEND`, so tests and demos can avoid Firestore's free-tier quota. State changes live once in `VideoRecord` update dicts that every adapter applies; one contract suite (`tests/contract`) runs against each backend. Production refuses `memory`.
- M3: Supabase must be reached through the session pooler: the direct host `db.<ref>.supabase.co` is IPv6-only and unreachable from IPv4 networks such as this WSL machine. The current project is in Sydney (about 0.3 s per query); use a Mumbai project for a deployment in `asia-south1`.
- M3: The Supabase contract tests run in a throwaway schema (`ishaara_test_<id>`) and drop it afterwards. They take about 12 s each because of that latency.
- M3: The Firestore adapter was first only type-checked (no Java or emulator here); it has since been verified against the real database, see the deploy entry below.
- M3: Single-writer updates (progress, lease, ready, failed) are partial writes without a read to save Firestore quota; only create, restart and quota use transactions.
- M3: The pipeline ends after merge and marks the video `ready` with cues that have no narration text or audio. Bump `PIPELINE_VERSION` to 2 when M4 lands so these cached results are not reused.
- M3: A user who loses a race between two first submissions of the same video has already spent one daily-video quota unit; this undercounts in the user's favour and was left as is.
- M3: `get_youtube_client` (M1) was removed; the `AppContainer` composition root owns the YouTube client. Quotas use the UTC date.
- M3: `GeminiError` (502, `gemini_error` / `gemini_invalid_response`) wraps SDK, network and parsing failures so business logic never imports `google.genai`.
- M4: The TTS call rejects `delivery: "inline"` ("Audio delivery mode is not supported"); `response_format={"type": "audio"}` returns a 24 kHz mono 16-bit WAV, as the plan said. `generation_config.speech_config=[{"voice": "Kore", "language": "en-US" | "hi-IN"}]` is accepted; whether `language` changes the output was not verified by listening.
- M4: `gemini-3.5-flash-lite` produced valid `NarrationBatch` JSON in English and Hindi (Hindi in Devanagari, with English loanwords transliterated, e.g. "काउंटर-क्लॉकवाइज"). `GeminiGateway.write_narration` / `synthesize_speech` now return `NarrationResult` / `SpeechResult` carrying token counts.
- M4: Stages 4-5 run after merge: one narration call, then speech per cue (4 in parallel, up to 3 attempts each). A cue that still fails keeps `audio_url=None` and the job succeeds, so the frontend falls back to `narration_text`. A failed transcript upload is logged and only loses the transcript (`transcript_blob_path=None`); the video still becomes `ready`. `PIPELINE_VERSION` default is 2 so M3's narration-less results are never reused.
- M4: Storage is behind a `BlobStorage` port with local, GCS and Supabase Storage adapters (`STORAGE_BACKEND`); production refuses `local`. Only the local and Supabase adapters have run against real storage. The GCS adapter is covered by fake-client tests only (no GCP credentials here).
- M4: Supabase Storage needs the **secret** key in `SUPABASE_SERVICE_KEY`. A `sb_publishable_...` key fails with a row-level-security error and an empty bucket list. The adapter sends the key as both `apikey` and bearer, which works with an `sb_secret_...` key. Public bucket `narrations` and private bucket `transcripts` were verified: a public file is fetchable without a key, a private one is not.
- M4: Real run (English lecture, 8.8 min, Supabase database and storage): `ready` in 220 s, 5 cues, all audio valid WAV with matching durations, transcript 147 segments up to 521 s, 55,734 input and 13,643 output tokens. Audio quality and Hindi pronunciation were not checked by listening.
- M4 follow-up (unresolved): cue sets differ between runs of the same video (7 cues, then 5; the 00:05 slide with agenda bullets was missed the second time). Experiment on a saved 3-minute clip: the gap judge (pass 2) is stable on clear gaps (5/5 runs, with or without `temperature=0`), but pass 1 describes the same slide differently from run to run ("a slide with white text" versus "slide title 'Circular Tracks' followed by two numbered items"). Hypothesis: a vague description is filtered out or judged weak. One sample per setting only. Ideas: optional `temperature`/`seed` for pass 1, a stronger "include the slide's text" instruction, and storing the raw pass outputs of each job for diagnosis.
- M4 follow-up (explained in M6, see below): one speech call stalled for about 80 s in the real run with no logged failure. Retries are now logged (`gemini_retry`), each voiced cue logs its elapsed time (`cue_voiced`), and the speech timeout is 30 s (was 60 s).
- M4: `configure_logging` no longer caches loggers on first use, so `structlog.testing.capture_logs` works regardless of test order.
- M5: Notes use `##` for the 5-minute sections under a single `#` title, not the plan's `###`, so heading levels are never skipped (screen readers and accessibility checkers flag skipped levels).
- M5: `cues.vtt` stays authenticated, as the plan says. A `<track src>` cannot send a bearer token, so the frontend fetches the file with the token and attaches a blob URL (documented in `docs/API.md`).
- M5: A cue without audio gets a VTT duration estimated at 0.4 s per word (minimum 2 s); every cue is clamped so it never runs into the next one.
- M5: Notes escape all text that comes from YouTube or Gemini and render Markdown with raw HTML disabled. If the transcript is missing or unreadable, the notes still return (board descriptions only) and say so, instead of failing.
- M5: `GET .../cues|cues.vtt|notes` share one dependency that answers 404 `video_not_found` or 409 `video_not_ready` (with the stage and percentage, "queued", or the failure reason). `BlobStorage` gained `download_private` in all three adapters, and `AppContainer` now holds the blob storage.
- M5: Not run here (no browser or Node): the `<track>` element check and the axe/Lighthouse accessibility check. Tests check the same properties structurally: a WebVTT grammar parser over the real output, and for the HTML a single `h1`, no skipped heading level, `lang`, `title`, a `main` landmark, and no injectable markup.
- M6: `QuestionAnswer` has a fourth field, `answer_language` (`en` or `hi`), not in the plan: the answer is written and spoken in the language of the question, so a Hindi question about an English-narrated video gets a Hindi answer and a Hindi voice.
- M6: The daily question quota is spent before the Gemini calls (the usage port has no refund), so a question that fails on Gemini's side still uses one of the 50. An `at_seconds` past the end of the video is rejected (422) before any quota is spent.
- M6: A failed visual check (video clip call) falls back to the text answer instead of failing the request; a failed speech call or upload returns the text with `answer_audio_url: null`. A visual check needs `at_seconds`; without it a board question is answered from the text only.
- M6: With no `at_seconds` the context is every cue description plus the transcript, cut at 40,000 characters (at a line boundary, with a marker). Answer audio is public at `answers/{video_key}/{random id}.wav` with a year-long cache header; the id is unguessable, not secret.
- M6 finding: Gemini's speech endpoint can stop responding altogether. In the real M6 check one call returned a 429 and later calls simply never answered (three attempts, each hitting the deadline). The SDK retries 429/5xx by default (up to 4 attempts, each with its own timeout) and the gateway's own retry sat on top of that, so waits multiplied into minutes; this also explains the M4 stall. Fix: the SDK client is built with `HttpRetryOptions(attempts=0)` so `tenacity` is the only retry layer (logged as `gemini_retry`), every attempt has a hard `asyncio.wait_for` deadline (call timeout + 5 s; a blocked worker thread cannot be killed but is no longer awaited), and a missed deadline becomes `GeminiError("gemini_error", "Gemini did not respond in time.")`. A speech call now fails after at most about 114 s; in the question path the answer waits at most 25 s for its audio (`SPEECH_BUDGET_SECONDS`) and is otherwise returned as text with `answer_audio_url: null`.
- M6 real check (video v8kBd64_WAc seeded from earlier real output, real Gemini text and video calls, Supabase storage): text, board, Hindi and no-time questions all returned grounded answers (Hindi answered in Hindi); a question at 8:20, where no cue or transcript covers the moment, triggered the visual check (`used_video: true`) and described the board. Answers took about 34 s each, of which 25 s was the speech budget expiring because Gemini speech was not responding, so no answer audio was produced or listened to. The visual question took 89 s in total.
- M6 not verified: spoken answers (speech was down), the accuracy of the visual answer against the video, and the ranking or quality of any open-source model (none was tried).
- M7: Request bodies over `MAX_REQUEST_BODY_BYTES` (16 KB) are rejected with 413 `request_too_large` in problem+json, before authentication, by a pure ASGI middleware that checks `Content-Length` and also counts streamed bytes. FastAPI converts any error raised while reading the body into its own 400, so the middleware remembers that the limit was exceeded and replaces the app's response with the 413. CORS is the outermost middleware so the 413 still carries CORS headers.
- M7: Every response carries `X-Content-Type-Options: nosniff`; `/v1` responses also get `Cache-Control: no-store` (they are per-user) unless a route sets its own.
- M7: A `video_key` in a URL must look like `<11-char id>_<en|hi>_v<n>`; anything else is `404 video_not_found` without touching storage. YouTube links containing control characters are rejected (`invalid_youtube_url`).
- M7: On SIGTERM the job runner cancels running jobs and sets their leases to "expired now" (best effort, 5 s limit), so the next request restarts them at once instead of waiting up to 90 s for the lease to run out. The Dockerfile starts uvicorn with `--timeout-graceful-shutdown 8` to finish inside Cloud Run's roughly 10 s. Verified with `docker stop`: exit code 0 in 0.6 s.
- M7: `docker build` now works (it could not be run before M7). The image holds only production dependencies and every module imports; `ENVIRONMENT=production` with the in-memory database exits immediately with a validation error. Docker's advisory about the shell-form `CMD` is deliberate: the shell form lets `$PORT` expand and `exec` hands signals to uvicorn.
- M7: `/healthz` only answers GET (HEAD returns 405); Cloud Run probes use GET.
- M7: `uv run ishaara process <urls> --languages en hi` pre-processes videos into the configured database and storage (as its own user, `cli-preprocess`, with its own daily limit), reports one JSON line per video and language (`ready`, `cached` or `failed`), and exits non-zero on any failure. It refuses `DATABASE_BACKEND=memory` (nothing would be kept). It was tested with fakes only; a real run needs Gemini quota and, for audio, a working speech service.
- M7: Firebase Admin is initialised with `GCP_PROJECT_ID` as its project id when that is set, instead of relying on it being guessed from the environment.
- M7: `docs/DEPLOY.md` and `scripts/smoke_test.sh` were written for Cloud Run. The script was exercised against a real local container (public checks pass, a dead URL fails with a non-zero exit code). **The deploy itself has not been run**: `gcloud` is not installed on this machine and no Cloud Run service exists.
- M7: Guard tests keep `.env.example` (every setting, matching defaults) and the README (every setting named) in step with `Settings`.
- Deploy prep: the Firestore adapters take an optional `collection_prefix` (empty in production). Setting `FIRESTORE_TEST_PROJECT=<project>` makes the contract tests run against that real project using a unique `contract_test_<id>_` prefix per test and deleting those collections afterwards; without it the Firestore tests need an emulator or are skipped. All 13 passed against the real `ishaara-v1` database (the default Native database in asia-south1), including the concurrent-quota and transactional-restart tests, and no test collections were left behind. This does not prove the Cloud Run service account's IAM roles; that is checked at deploy.
- Deploy prep: the `ishaara-v1` project had Firebase, Firestore, Identity Toolkit and the YouTube API enabled but **no billing account**, so Cloud Run, Cloud Build, Secret Manager and Cloud Storage buckets could not be enabled or created yet.
- Deploy prep: settings are layered `.env` (shared) then `.env.<ISHAARA_ENV>` (default `local`; `prod` for production), with real environment variables on top; a missing file is skipped. Local development uses Supabase (database and storage); production uses Firestore and Cloud Storage. Every `.env*` file except the `*.example` templates is git-ignored and excluded from the Docker image (`.dockerignore` and `.gitignore` were extended first, because `.env.local` and `.env.prod` were not covered by the old single `.env` rule). The deployed service never reads these files: `scripts/deploy.sh` (`DRY_RUN=1` prints the command) builds `--set-env-vars` from the plain settings and `--set-secrets` from Secret Manager names via `ishaara deploy-env`, and refuses a configuration the app would not start with. The app logs `settings_loaded` (environment, database and storage backends, no secrets) at start.
- Deploy prep: state of `ishaara-v1` after setup: billing linked; APIs enabled (Cloud Run, Cloud Build, Artifact Registry, Secret Manager, Cloud Storage, plus API Keys and Generative Language); service account `ishaara-api` with `datastore.user`, `objectAdmin` on its two buckets only, and read access to its two secrets; buckets `ishaara-v1-narration-audio` (public read) and `ishaara-v1-transcripts` (private) in asia-south1; secrets `gemini-api-key` and `youtube-api-key`; the existing default Firestore database. The Google Cloud Storage adapter was verified on those real buckets (public fetch without credentials works, the private object returns 403 publicly, a missing file maps to `StorageError`). Not yet done: the Cloud Run deploy itself.
- Deploy prep: the Gemini key in the secret is the existing AI Studio key from `.env`, so it keeps free-tier quotas and Gemini speech may still stall. A project-billed key was created and then deleted unused; creating one is `gcloud services api-keys create --api-target=service=generativelanguage.googleapis.com` and a new secret version.
- Deploy: Cloud Run reserves some paths ending in `z` (including `/healthz`) and answers them with Google's own 404 before the request reaches the container, so the plan's `GET /healthz` cannot be used there. Found on the first deploy; the app now serves `GET /health` as well (both return the same body), the smoke test and docs use `/health`, and `settings_loaded` reports the env files actually found (an empty list in the container) instead of an `env_name` that showed the default `local` there.
- Postman: the collection was rebuilt (6 numbered folders, 25 requests, 33 saved examples, a collection-level problem+json check, automatic polling in the Collection Runner, captured `videoKey` and `audioUrl`) with a local and a Cloud Run environment. It was run with Newman against a local server on a seeded ready video (21 requests, 48 assertions, 0 failures) and the token-free requests against the live service. That run found a real bug: the cue-audio request was built from URL parts, which appended a trailing slash and made object storage answer 404; it now uses a plain string URL. Folders 2 and 4 (Gemini) were not run through Newman, and nothing was run in the Postman desktop app.
- Production test (two real videos on the live service) found two bugs and one cause, all fixed: (1) the Interactions SDK raises its own exception family (`RateLimitError`, `APITimeoutError`, ...), which is not a subclass of `google.genai.errors.APIError`, so the gateway neither retried nor cleanly reported any real API error and jobs ended as `internal_error`; unit tests had used stand-in exceptions and could not see it. The gateway now classifies the real classes (by name and `status_code`, no private imports), retries 408/409/429/5xx, timeouts and connection errors, and maps everything else to `GeminiError` with the HTTP status. (2) A 429 was retried after 1 to 2 seconds although Gemini says "retry in 59s"; the wait now follows the hint (header or message, capped at 70 s). (3) The cause of the speech stalls seen since M4: the free-tier key allows **3 speech requests per minute** (`gemini-3.8-flash-lite-tts`), and the pipeline sent 4 in parallel per video. A process-wide `RateLimiter` (`TTS_REQUESTS_PER_MINUTE`, 0 = unlimited, 3 in `.env.prod`) now spaces speech calls, and each retry takes a slot too. The per-process limit is not shared across Cloud Run instances. Also: the analysis call timeout went from 180 s to 300 s after a 5-minute video exceeded 180 s once.
- Production test: the live service accepted a real Firebase ID token from a temporary email/password user (`200`) and rejected a tampered one (`401 invalid_token`); the user is deleted afterwards.
